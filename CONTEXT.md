# Context

This repository, house-rules, is the home of the house plugin, and of a template, the stack. It holds no product-specific code, meaning no domain logic of any app. It does ship reusable libraries to npm under the `@house-rules` scope: `packages/rules`, `packages/domain`, `packages/application`, `packages/migrations`, `packages/call-audit`, `packages/comments` and `packages/node-host`, which apps install by exact version. The six TypeScript libraries ship **built** JavaScript in `dist/`, so an app needs no bundler step to compile them. In this repo they stay source: `exports` names `src/`, and `publishConfig.exports` names `dist/` for the published manifest. `@house-rules/capability` is the **retired package** the two kits replaced: it stays at 0.16.0 on npm and gets no new versions.

The framework has four parts. The **kits** are the two libraries an app builds on. The **domain kit**, `@house-rules/domain`, defines domain modules: `defineModule`, the Actor, permissions and policy, and the unit of work. It imports no house-rules package. The **application kit**, `@house-rules/application`, builds the application layer on those modules: contracts and capabilities, `CurrentActor`, the gates, the call watch, composition and delivery. It depends on the domain kit, never the other way. The **wiring** joins and runs an app: `@house-rules/migrations` runs every module's SQL, `@house-rules/node-host` serves the app on Node, and `@house-rules/rules` checks it, at dev time only. The **additions** are reusable parts an app mounts: a **domain addition**, such as `@house-rules/comments`, is a module with its own data, and a **plug-in**, such as `@house-rules/call-audit`, fills a slot. The fourth part is the app itself.

The **house plugin** is the `@house-rules/rules` package in `packages/rules`. It owns the **house rules** and the **presets**: the ESLint rules, the TypeScript and Biome presets, the Dependency Cruiser `layout()` factory, and the `house-rules-pins` and `house-rules-migrations` bins. The template root uses it as a workspace package, `workspace:0.18.0`. Other apps install it from npm at an exact version. No rule code and no copy of a preset lives outside `packages/rules`.

A **web app** is an app whose UI a bundler builds, with Next.js, Vite, Remix, Astro or similar. It uses the presets with no local exceptions. Its UI tsconfig extends the **web preset**, `tsconfig/web.json`: DOM libs and bundler resolution, no plugin block. Its Effect code, the composition, server and use-cases, gets a second tsconfig that extends `effect.json` and then `web.json`. The Biome preset parses Tailwind v4 directives. Its pages reach use-cases through the composition and the delivery adapters, never through the server folder. In `layout()`, its **generated declaration files** (`generatedDeclarationFiles`) may import build output that does not exist yet. A **Host** runs an app's delivery. The Node Host, `@house-rules/node-host`, listens on a Node HTTP socket and streams Web Requests and Responses through a fetch handler. It is plain TypeScript on the strict preset, so Effect apps never import `node:http`. A Next app already has a Host and needs no Node Host package. For web layout, a **host** is the framework that runs its delivery; `layout({ host: "next" })` and `shadcn({ host: "next" })` know Next's own files (`src/app/` as delivery, `proxy.ts`, `instrumentation.ts`, `next-env.d.ts`, `.next/`, and `app/global-error.tsx`, a **shell-free file** that renders outside the app shell), and its tsconfig extends `tsconfig/next.json`. Its design system lives in a **component folder**, such as `components/ui`: `shadcn()` reports a **raw element**, such as `<button>`, where that folder has a component for it, and `design()` can keep every app style rule inside an **allowed layer** with `design-css-layers`.

The template is a showcase of the house plugin wired into a real workspace. The plugin gives the deterministic feedback, and its README lists every checked rule. The template adds five things:

1. **Thin configs**: `tsconfig.base.json`, `biome.json`, `.dependency-cruiser.cjs`, and `eslint.config.mjs`. Each points at a preset and sets only **project values**, such as the `@example/` scope, the example roots, or Biome's own excludes.
2. **Stack-only files**, which no package can hand down: `turbo.json`, `pnpm-workspace.yaml`, `.env.schema`, CI, `lefthook.yml`, and the agent-harness hooks.
3. Prose: `AGENTS.md`, `CONTEXT.md`, `README.md`, `VISION.md`, and `skills/house-rules/`, the one agent skill. The **prose rules** in `README.md` are what a reviewer checks, because no tool can.
4. The **example**, `examples/booking-platform`: a private **showcase** laid out like a regular project, with its app in `apps/api` (`@example/api`) and its package in `packages/bookings` (`@example/bookings`). It is never published, framework packages never import it, and a new project deletes `examples/`. `packages/rules` is the plugin, not example code, so the layout rules do not apply to it. `packages/domain` and `packages/application` are libraries, not example code, and the layout rules apply to them like any package.
5. **Wiring tests** under `tests/`, which prove the thin configs and the fence are hooked up, not how each rule behaves. The plugin tests its own rules.

The repository is a pnpm **workspace**: one root with one lockfile, plus workspace packages listed in `pnpm-workspace.yaml`. Turborepo runs each workspace package's `typecheck` and `test` scripts in dependency order. A **workspace package** is any folder under an apps or packages root with its own `package.json`. `apps/` and `packages/` are where a project keeps its own code; in this repo, `packages/` holds the framework packages, and `examples/*/apps` and `examples/*/packages` are two more roots for the example. An **app** is a workspace package under an apps root. It holds delivery, server, and use-case code, and nothing imports it. A **package** is a workspace package under a packages root. It holds one module, and apps and other packages import it by its package name through `src/index.ts`, its public entry. Packages may depend on each other, but the package graph has no cycles and no fixed levels. The `no-package-cycles` check enforces this. A package calls another package's service; it never reads that package's tables or SQL.

A **support module** is a domain addition: it solves a reusable app need and exposes methods that the app wraps in its own use-cases. It is not a cartridge: those use-cases depend on it. The first is `packages/comments`, the public `@house-rules/comments` package, mounted against Bookings through a host port in the API composition. Its 0.1.0 first release is prepared here, not yet published. It keeps the same package boundary.

A **module** is a piece of behavior with one **interface** and a private **implementation**. The interface is the small set of imports callers need. The implementation stays behind it. A **seam** is the location of that interface. **Depth** is the useful behavior a caller gets for the amount of interface it must learn. In this repo each module is a package, so a package's **public entry** is its seam: `src/index.ts`. A package may add one **contract entry**, `src/contract.ts`, exported as `"./contract"`: the browser-safe part of its interface, its contracts, schemas, errors and permissions, which reaches no adapter, facade, storage port or server code. Its `package.json` `exports` names only those two.

The checked example puts the bookings module in `examples/booking-platform/packages/bookings`, named `@example/bookings`, and the app that uses it in `examples/booking-platform/apps/api`. The app's delivery and use-cases import `@example/bookings`. They may not import any other file of the package: every file but `src/index.ts` is private. The module's storage lives in its `src/adapters/`.

Modules are cut by life cycle, not by noun. A package holds one module cut around a consistency and access boundary: everything that only exists inside it, such as Trippy's trip with its days, items and shares. A thing with its own life gets its own module. A package can use another package through its public entry and service, but never its tables or SQL.

Use-cases are the app's feature list. One use-case is one thin feature exposed through delivery, such as HTTP, MCP or CLI. It may call several packages and opens the unit of work.

Inside a package the code is cut by **subject**. A **subject folder** is a folder directly under a package's `src/` that holds one subject's schema, errors and logic, such as the example's `packages/bookings/src/booking/`. Every package uses subject folders, even one with a single subject. The **root subject**, or **shared kernel**, is the subject that holds the ids and errors other subjects use, such as Trippy's `trip/`, so subjects import each other in one direction. Next to the subject folders, `src/` holds only `index.ts`, `facade.ts`, `storage.ts`, `adapters/` and `tests/`. A **mechanism name** is a file or folder name that says what kind of code a file holds instead of what it owns, such as `types`, `models`, `schemas`, `drafts`, `errors`, `validate`, `validation`, `constants`, `interfaces` or `internal`, in any letter case; a package uses none.

In the example, a module's **service** is its interface: a `Context.Service` class, such as `Bookings`, declared with **defineModule** from `@house-rules/domain`. It binds one stable id, the service key, to methods returning Effects with no requirements. Its **make** captures long-lived dependencies when the Layer builds, never a request's `CurrentActor`. An Effect make gives a Layer value; an options function gives `layer(options)`. Presets are plain data and adapter statics stay on the class. Effect owns lazy build, sharing within one build and scoped cleanup, with no global cache. This is for root modules only; one module per package stays the rule. An **expected error** is a `Schema.TaggedError` class, such as `BookingNotFound`, carried in the Effect error channel. A **layer** in Effect code means an Effect `Layer` that provides a service. It is not a delivery, server, or use-case layer of an app.

An **Actor** is the user a call acts for. A service method that acts for a user takes the Actor as an explicit argument, and checks access itself. **CurrentActor** is the Effect service that holds the Actor for one request. A use-case yields `CurrentActor`, so it never learns how the user signed in. The domain kit exports Actor as a schema with one branded ActorId string; the application kit exports `CurrentActor` as a service that yields the Actor directly. The **per-request marker**, `PerRequest` in the domain kit, tags a service that holds one request's value. `CurrentActor` carries it, and `defineModule` refuses a make that requires a marked service, so the domain kit never names `CurrentActor`. Bookings takes the Actor in `create` and `relation`; it captures no request identity.

An **adapter** is delivery code that lets one kind of caller reach the use-cases. It decides who the `CurrentActor` is, runs a use-case, and maps its typed errors to its own response. A web page behind a cookie session is one adapter. An MCP server is another, and a CLI would be a third. An MCP **tool** is one action an agent can call: a name, a description, an input schema, an annotation that says whether it only reads, and a handler that runs one use-case. The **tool catalogue** is the list of tools in one app's delivery layer. A **resource server** checks OAuth tokens that an outside authorization server issued, and never issues them itself. A remote MCP server is one.

A **capability** is one named action an app offers, such as showing a booking. It pairs a **contract** with one handler. The contract holds the name, a description, Effect Schemas for the input, the output, and the failure, two flags, `readOnly` and `destructive`, a permission, and whether the call needs approval. The handler is an Effect, like a use-case: it takes the decoded input and gets its services from layers. A module knows nothing about capabilities, and its service is the interface callers use. A capability is one action offered on top of that service. A contract declares its permission. Checks of one object, such as whether this user owns this trip, stay inside the module, next to its data. The application kit, `@house-rules/application` in `packages/application`, defines both. Apps outside this repo install it from npm at an exact version, as they do the house plugin. Every use-case is a capability. A **surface** is what an outside caller reaches, such as an MCP tool, an RPC, or an HTTP endpoint. Each surface comes from a contract: `toTool` builds an MCP tool from one.

The **composition** is the app's one root object, `composition({ layer, caller, views })`, in `src/composition/` with its callers and views. It builds the app layer once, so every adapter shares the same services and pools. A **layer error** is a tagged error the app layer can fail to build with, such as a database that is down. It has a view in the views table like any failure, and a failed build is not kept: the next use builds again. Disposing the composition is final: it stops the requests still running, closes the layer, and every later request answers `CompositionClosed`, a 503. A **caller** turns an incoming request's headers and URL into the per-request services, usually `CurrentActor` and the Grant, or fails with `Refused`; `admit` runs this step before parsing input. A **cookie write** is a write request that carries a `Cookie` header, whatever its caller; the fetch adapter checks its Origin against CSRF. A **view** is the answer one typed failure gets: a status, a body, maybe headers, and maybe a public failure code. A success has no view: its body is the encoded contract output. An **input issue** is the kind of input fault an `InputInvalid` names, beside its capability and field: `unexpected`, `missing`, `invalid` or `repeated`. The **query dialect** is how a GET query maps to a contract's input: one key per scalar field, and a **repeated key** per item for an array field. The app's **views table** maps each failure tag to its view, and every adapter reads it, so a `BookingNotFound` is a 404 over HTTP and the same body as an MCP tool error. `toFetchHandler`, `toMcpHandler` and `call` are the **delivery adapters**: Web fetch, MCP, and an in-process call for React server code. An **endpoint** is one contract at one HTTP method, path and success status, made with `endpoint(contract, "GET /x/:id")`. A route mounts a capability at an endpoint, `toHttpClient` turns endpoints into a typed **HTTP client** for a single-page app, and `toOpenApi` describes them as OpenAPI 3.1. The client gets a failure back as an `HttpFailure`: a public **failure code**, and the view's status and body. A failure code goes out in the `x-failure-code` header only when the view exposes it and the endpoint declares it; the client calls every other failure `Unknown`. That double opt-in gates the header only; the view's body goes out as its author wrote it. The error's tag never crosses the wire. Status 500 belongs to **defects**: a view that answers 500 sends the generic `internal_error` body, and its own body goes to the log.

Each call to a capability answers four questions in order. Who calls? The adapter answers by building `CurrentActor`. May this caller do this at all? The Grant answers. Does a human mean it, now? Approval answers. May the caller act on this one object? The module answers, with its own data.

A **permission** is a `resource:action` string, such as `bookings:read` or `trips:delete`. The module that owns the resource names its permissions, and several capabilities can share one. Every contract declares a permission, or says `"public"` on purpose. The **Grant** is the slot that answers whether this caller holds a permission at all. It runs before any data is read, so it cannot leak whether a record exists, and it fails with `Forbidden`. An **app role**, such as member, admin, or a paid plan, is a fact about the caller with no object. It feeds the Grant. A quota, such as five trips at most, is not a permission: it needs a count, so it lives in a module. The Grant is **action-level authorization**: a fixed step of `implement`, whose answer is a slot.

**Approval** is the slot that asks a human whether they mean this call. It is **consent**, not permission, and a fixed step of `implement` too. A contract with `needsApproval: true` asks for it, and a refusal fails with `ApprovalDenied`. On MCP the elicitation cartridge fills it with a field-less form shown by the client, where Accept is the yes, so an agent can never answer its own approval. `implement` runs the Grant, then Approval, then the handler, and adds each gate's slot and error to the capability's types. The adapter fills both slots for each request, the way it provides `CurrentActor`. A Grant or Approval that is the same for every request is provided by the composition root instead.

A **relation** is how the caller stands to one object, such as owner or shared of Trip 7. `Bookings.relation(actor, id)` answers `"owner"` or `"none"` from the stored ownerId fact. Missing and legacy bookings, whose ownerId is null, answer `"none"` for everyone. Public booking reads remain visitor-readable and omit ownerId. A **policy** maps each relation to the permissions it carries. It is **object-level authorization**, and it lives inside the domain module, not in the application kit. The module owns its policy and checks the relation against its own data, and a "not yours" answer looks like "not found". `definePolicy` gives the shape and a who × action table for tests. An **object state** is how the object itself stands, such as a Trip that is active or frozen because its owner stopped paying. A policy with states lets a permission through only when both the relation and the state carry it, and its table adds the state as a third axis. A plan, such as free or paid, is not an object state: it is a fact about the caller and feeds the Grant.

A **storage port** is the service a module's domain code uses to read and write its data, such as `BookingStore` in the example's `packages/bookings/src/storage.ts`. The module defines it in its own words. The port answers facts, such as a row or its owner id, and never decides a permission, a standing, or a limit: the domain code decides. A **storage adapter** is a layer that fills the port. The **Postgres adapter** in `src/adapters/postgres/` holds the module's plain SQL and decodes each row with a Schema. The **memory adapter** in `src/adapters/memory/` keeps the same facts in plain data, for tests and scripts. Only files under `src/adapters/**`, and the **adapter packages** a repo names, such as the migration runner, may import SQL, a driver, or platform code. One **shared store suite** in `src/adapters/tests/` runs every store case on both adapters, so they cannot drift apart.

A **unit of work** is one transaction the use-case opens, the way `UnitOfWork.atomic` does. A contract that sets `transactional: true` gets one around its handler, after the gates. A unit may span several modules, so a failure rolls back all their writes together. A module never opens one: its write method calls `UnitOfWork.required`, joins the open unit, and fails with `NoOpenUnit` when none is open. For `transactional: true`, `implement` removes `NoOpenUnit` from the handler's error type and treats it as a defect: the unit is guaranteed. A non-transactional handler keeps that typed failure. The domain kit defines the `UnitOfWork` slot. The **SQL unit** (`sqlUnitOfWork`, in the application kit) is a Postgres transaction. The **memory unit** (`memoryUnitOfWork`, in the domain kit) runs no transaction: it runs the work and, when it fails, calls the undo hooks the memory stores registered with `UnitOfWork.onRollback`.

A module owns its **migrations**, the `.sql` files in `packages/<name>/migrations/`, and the **tables** those migrations create. Its **owning package** is the one whose migration creates a table. No other module holds a foreign key to the table or names it in SQL.

The **module list** is `migrations.json` at the repository root. It names every module whose migrations the app runs, as an array of **entries**. A **workspace entry** names a workspace package, whose migrations sit in its `migrations/` folder. A **framework entry** names an installed package, such as `@house-rules/call-audit`, whose `package.json` declares its **migrations folder** under `houseRules.migrations`, and which ships that folder. Each entry gets a **history table**, `<module>_migrations` unless the entry names another, where the runner records what it applied. No two entries share a module name or a history table. `@house-rules/migrations` runs the list in one transaction, and `house-rules-migrations` fails when a module with migrations is missing from it. An entry may **adopt** its rows from an older **old history table**, one that several modules used to share: its `adopt` key names that table, the ids it owns, and the ids to **rehash**, files edited on purpose whose digest the run fills again. The runner copies the rows once, while the module's own history table is empty, and only reads the old table.

The words for wiring come from ports and adapters. A **port** is a **slot**: a service tag, a `Context.Service` class such as `Bookings`, that says what a caller needs. A **layer adapter** is a `Layer` that fills a slot, such as `Bookings.fromRecords` or a Postgres layer for the same tag. A **storage adapter**, defined above, is a layer adapter for a module's storage port. The delivery code above that lets a caller reach the use-cases is the other kind of adapter, a **delivery adapter**. When the context does not make it clear, say which one. The **composition root** is the one place in an app that provides services and slots: `src/composition/`, the **composition layer**. It imports packages only; delivery, server and tests import it, and a use-case never does. Delivery provides only per-request values: `CurrentActor`, the CallChannel, the request id through `withRequestId`, and the Grant and Approval an adapter fills for this one request. A module service, a storage adapter, and any slot that is the same for every request belong to the root. A **host port** is a slot a domain addition defines and the app's composition root fills, such as `CommentTargets`. The **call watch**, `CallWatch`, is the only **middleware**: it wraps every call and never changes the result. A **cartridge** is one job plus its own infrastructure, packaged so it pushes in with one `Layer.provide` line and pulls out by deleting its package and that line. The **pull-out test** asks whether the rest still builds and passes once it is gone. A reviewer runs it; no tool does.

The runtime packages use stable Effect 4.0.3 with exact peer pins: domain 0.1.0, application 0.1.0, migrations 0.3.0, call-audit 0.6.0 and comments 0.1.0. These are release-ready workspace versions, not a claim that the next releases are live. Node Host 0.1.0 has no runtime dependencies. Rules 0.18.0 takes several apps and packages roots, recognises the kits by their new names, and fences the stable `effect/sql` imports and hand-built AI, RPC and HTTP API calls as it does the RC paths. The **cold consumer** installs packed packages plus the Node platform into a fresh directory without a lockfile; it checks the shared Node version, runs the entries and type-checks the app. A **published package tag**, `@house-rules/<pkg>@<version>`, marks only a package this publish run shipped, from pnpm's report. The job pushes through `GITHUB_TOKEN`, which does not trigger workflows.

The **agent sources** are shallow clones of dependency source under `.agent_sources/`, made by `pnpm vendor:agent-sources`. Agents read them. Nothing imports them.

The **fence** is what stops an agent from skipping the checks: exact pins, `pnpm check`, `pnpm test`, the lefthook pre-commit hook, and the harness hooks that block `git ... --no-verify`. Its code lives in `scripts/` and `.pi/extensions/`. **Law** is `AGENTS.md`. **Vision** is `VISION.md`, and each project made from the template writes its own.

The **docs site** is `site/`, the workspace package `@house-rules/site`, served at `stack.kubaszwajka.com`. It is for people deciding on the template and starting a repo from it; agents read `AGENTS.md` in their own repo. It has two pages besides the home page: the **start page**, written by hand, and the **rules page**, a **generated page** the site's generator writes from the plugin's rules table, one row per rule. Each row's **rule anchor**, `/rules/#<rule id>`, is the link error messages use. `llms.txt` names the two pages and sends agents to `AGENTS.md`.
