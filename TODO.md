- [ ] **Migration plan for releases.** Add `house-rules-migrations plan --from <sha> --to <sha>`. It reads every `packages/*/migrations/*.sql` at both commits through git, computes each migration's id, name and SHA-256 the way the runner records them, and prints `{"pending": [...], "edited": [...], "removed": [...]}`. Exit 0 when the plan is computed; exit 1 when a migration was edited or removed, which blocks the release. It compares content, not paths, so a byte-identical move (Trippy v0.11.0) is `pending: none`. `--from` is the commit prod runs, read from its health `.commit`, not the last tag. Then the release flow uses it: the fleet field for a house-rules repo becomes `migrations: house-rules-plan` instead of folder paths, the release skill runs the plan in a shallow clone for the readiness report (`pending: none` means auto rollback is allowed), and `fx release verify` reads the migrator's startup line ("applied none" or "applied 6_spots") to confirm prod did what the plan said. The plan trusts that prod's database matches prod's code; the startup line catches drift. Repos not on house-rules keep explicit paths, or ship a plan command with the same output. Until this ships, Trippy's fleet entry names `packages/trips/migrations`.
