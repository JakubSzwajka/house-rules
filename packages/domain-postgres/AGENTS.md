# Agent guide: @house-rules/domain-postgres

A Postgres `Platform` for Alchemy Domain (`@alchemy.run/domain` 2.0.0-beta.85, Effect 4.1.2). Swap it in where an app would use `Domain.InMemory`; the model does not change.

## Wiring

```ts
import { fromEnv } from "@house-rules/domain-postgres";

const Hosted = App.layer(AppHandlers).pipe(Layer.provide(fromEnv({ schema: "app" })));
```

- `fromEnv({ schema })` reads `DOMAIN_STORE` (`postgres` by default, or `memory`) and `DATABASE_URL`. Declare both in the app's `.env.schema`.
- `layer({ schema })` is the same store without the env switch; provide a `PgClient` yourself.
- By default `layer` and `fromEnv` create the schema and tables on start. That needs CREATE on the database or schema. When the runtime role may only read and write rows, the schema owner runs `migrate(schema)` in the migration step, and the app passes `createTables: false`. Start then only checks the tables and dies with `TablesMissing`, naming the schema and missing tables, if any are absent.
- The runtime role needs `USAGE` on the schema, `SELECT, INSERT, UPDATE, DELETE` on its tables, `USAGE` on its sequences (`outbox.position` is a `bigserial`), and `ALTER DEFAULT PRIVILEGES FOR ROLE <owner> IN SCHEMA <schema>` granting the same on tables and sequences the owner adds later. The README has the SQL.
- `migrate` checks the catalog before adding `view_keys.filled_generation` or `views.catch_up`; migrated tables must not undergo repeated owner-only ALTER.
- Apps with `createTables: false` run the owner `migrate(schema)` and grants before the server starts. Measure startup on production-sized history before deploying 0.2.0.
- Tests provide `platformForTests`: a fresh `test_<uuid>` schema per test, dropped after. Run the suite again with `DOMAIN_STORE=memory` to cover `Domain.InMemory`.

## Fixed rules

- Run one replica per schema. Two processes would both run the outbox loop and the schedules, so a policy could fire twice. Schedule firing locks the aggregate instance before deleting its schedule token, matching schedule and unschedule lock order.
- No projections, streams or sagas. Building a model with them fails.
- New or bumped eager targets replay stored source history before the model starts schedules, outbox delivery or client commands. Eager means no `kit.catchUp`, including single-source generation-zero views. Unchanged legacy generations without progress adopt a completed baseline without changing snapshots or entries. Adopted completion means no pending replay, not gap-free pre-0.2.0 history. Old holes need an explicit generation bump. Persist pending replay intent atomically with new/bumped metadata and resets; bind its JSON `null` plan at startup under the progress lock. Never adopt interrupted pending jobs as legacy; resume their cursors. Never blindly reset same-generation source logs that pending consumers may reference. The `backfills` table persists each generation's plan, cursor, completion and routed/applied/deduped counts. Replay source views before their consumers, then source name, source id and per-stream `seq` in bytewise order. Completion checks persisted per-delivery checkpoints, verified exhaustion and a key when `routed > 0`. The count equality is accounting sanity, not proof of gap-free pre-0.2.0 history.
- Persist each observed lazy/eager mode in nullable `views.catch_up`. A known lazy-to-eager transition re-arms the actual eager target atomically with mode metadata, preserving snapshots, entries and bound plans. Repeat transitions rescan; ordinary eager restarts preserve pending cursors. NULL means unknown prior mode and retains legacy adoption. Switching an unrecorded lazy declaration on the first upgrade needs an explicit generation bump. Batch empty eager startup only without model events, view entries, view keys or prior replay progress; retain the committed pending intents and normal 128-row pages for nonempty history.
- Bump a consumer's version when its replay plan changes, including `from` or upstream view generations. At the same consumer generation, changed persisted plans raise `BackfillPlanChanged` at startup even after completion. Alchemy propagates upstream generations into consumer generations. Keep persisted plans and same-generation logs intact.
- Source-keyed `kit.catchUp` views fill lazily per key on ordinary reads, entry scans and receives. Poison history fails reads instead of serving stale snapshots. Only keys needing history take a fill transaction and row lock. Replay that aggregate id's events in `seq` order before live batches, then set `view_keys.filled_generation` atomically. Filled-key reads check the persisted generation without locks or writes. Non-lazy reads remain one-query and non-transactional; unknown lazy ids without events do not persist keys. Notify and kick after the fill transaction commits. A downstream startup scan reads every stored lazy source id, even after downstream completion. Eager replay and lazy fill promote matching pending live deliveries for the current generation, preserving queued live view-policy effects. Old-generation history policies stay suppressed; original live deliveries are checkpoint-deduplicated and acknowledged later. `ModelHost.history` checks per-key completion. Pinned Alchemy beta.85 reports public self-filled `View.history` complete per accessed key; it is not global fill progress.
- SQL failures, including typed errors and defects, never consume outbox delivery attempts. The worker logs failures and retries with capped jittered backoff. Commit kicks cannot skip database or handler retry delays. Handler failures, including self-interruption, retain ordered retry and `maxAttempts` parking. Handler retries have no poll-interval floor. Real scope shutdown interrupts promptly without consuming attempts. Persistent SQLSTATE classes `22`, `23`, `42` and `54` still block the model drain without parking until repaired. Alert on `available: false` and repair the logged SQL fault.
- A parked view row blocks later rows for the same target kind, name, generation, `inPlace` value and key. Other partitions can proceed. Policy parking is unchanged.
- The optional `outboxStatus` callback on `layer` and `fromEnv` exposes a read-only per-model monitor with `parkedCount`. Treat a nonzero parked count as unhealthy. Cached observations are not a fresh database health check. Without this callback, skip status-observation SQL, not delivery selection or error logging. Memory mode does not create a Postgres monitor.
- Pin `@alchemy.run/domain`, `alchemy` and `effect` to this package's peer versions. The `Platform` contract is beta; rerun the tests on every Alchemy bump.
- A policy command id comes from its event, so a redelivered event is deduplicated by its receipt. A call to an outside provider inside a policy is not; make it idempotent.
