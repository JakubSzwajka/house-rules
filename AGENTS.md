# Agent instructions

This file is the law for agents and people working in this repo and projects made from its template. Read `VISION.md` for why and `CONTEXT.md` for the words. Vision does not override the law.

House rules and tool presets belong in `packages/rules`, the plugin `@house-rules/rules`. The root uses `workspace:0.18.0`. Keep consumer configs thin: extend presets and set project values. Never copy a preset into a thin config.

## Commands

Use the exact pnpm version in `package.json`. Do not replace it or add a second lockfile. Corepack selects the pinned version.

| Command | What it does |
| --- | --- |
| `pnpm install --frozen-lockfile` | Install the lockfile, patch tsc with `effect-tsgo patch`, install lefthook through prepare |
| `pnpm check` | Exact pins, module-owned SQL, environment, Biome, ESLint, Dependency Cruiser, production folder/package cycles and workspace typechecks |
| `pnpm test` | Root Node tests, then workspace tests through Turborepo |
| `pnpm run layout` | Subject, package and app-feature cycles |
| `pnpm env:check` | Resolve and validate `.env.schema` with Varlock |
| `pnpm exec varlock run -- <cmd>` | Run with validated environment values |
| `docker compose up -d` | Start Postgres; each database test creates and drops its own database through `TEST_DATABASE_ADMIN_URL` |
| `pnpm fix` / `pnpm format` | Rewrite files with safe lint fixes / formatting only; run only when intended |
| `pnpm build` | Build the nine TypeScript framework packages to dist for packing; workspace imports still read src |
| `pnpm acceptance` | Clone committed HEAD into a temp folder and run frozen install, check and test |
| `pnpm run packed-consumer` | Pack all ten public packages, install in a cold npm consumer and prove Node, TypeScript, browser contracts and layout behavior; needs the registry |
| `pnpm vendor:agent-sources` | Clone the pinned Effect source into `.agent_sources/` |
| `pnpm --filter <package> add <dep>` | Add an exact dependency pin to one workspace, after approval |
| `pnpm --filter @house-rules/site generate` | Regenerate the existing rules page |

CI starts Postgres and runs frozen install, `pnpm check`, `pnpm test`, `pnpm run packed-consumer`, the booking API build and the site build. The booking example serves a Vite/React shadcn dashboard with real sign-in; its build writes the page to dist/web and bundles the API.

Before calling work ready, `pnpm check` and `pnpm test` must both exit 0. Warnings fail Biome and ESLint; all Dependency Cruiser rules have severity error. The rules table in `packages/rules/README.md` is the checked-rule source. Do not duplicate it in the root README. Prose rules there still need review.

## Kits, wiring and additions

The kits are `@house-rules/domain` and `@house-rules/application`. Domain owns `defineOperation`, operation descriptors and edges, `PersonCaller`, `SystemCaller`, their union `Caller`, kinds, pure graph checks, closures, modules, policy and units of work. It imports no house-rules package, including type-only imports or application/contract. Application owns `defineFeature`, `bindOperation`, `runFeature`, `Runtime`, `CallerContext`, sockets, ways, the router, clients, trace and registry. Import a name from the kit that owns it; no cross-kit aliases or re-exports.

Wiring is migrations, Node Host and the dev-only rules plugin. Additions are reusable domain modules such as comments, party and identity, and plugs such as auth-jwt and call-audit. Identity is one configurable concept with passwords and OIDC providers. It owns login bindings and local password records, pairs each issuer with its auth-jwt verifier, and never learns roles. Auth-jwt remains a separate pure token-checking plug, including for MCP. A module keeps its own data; a plug fills a caller-owned port and passes the pull-out test. Removing a plug and its `Layer.provide` line must leave the rest building and passing. This is a review rule, not an automated check.

The four socket interfaces are `WhoSocket`, `MaySocket`, `MeanSocket`, `RecordSocket`. There is no export named Record. `Identity.who` answers Who using lower `Authenticator`, `ActorResolver` and `FirstSignIn` slots. Composition plugs one May with `Party.may()`. It resolves a person's roles on each call. `May.context` supplies the app May and exposed features for in-process execution; `May.system` supplies system permissions without person authority. `Mean.no`, `Mean.elicitation`, `Mean.allow` wrap lower Approval layers. `CallAudit.record.memory/postgres` supplies a RecordSocket over lower CallWatch. Keep Authenticator, Approval and CallWatch as separate slots.

## Workspace and package doors

- Apps live in `apps/<name>`, shared packages in `packages/<name>`. The private showcase belongs in `examples/booking/apps/api`. Framework packages never import examples (`framework-does-not-import-examples`). New projects remove examples. Workspace roots are declared in `pnpm-workspace.yaml` and passed to both `layout()` and `featuresConfig()`.
- A package never imports an app. An app never imports another app. Import another package by its declared name and an exact `workspace:<version>` pin, never a relative path. The production package graph has no cycles and no fixed levels.
- A package exports `src/index.ts` under `.` and may export `src/contract.ts` under `./contract`. Everything else is private. No export patterns or other subpaths. `publishConfig.exports` may point to the corresponding dist JavaScript and declarations. `house-rules-layout` checks the manifest as well as imports.
- Contract doors contain browser-safe descriptors, schemas, errors and permissions, never bindings, facades, storage or adapters. `contract-entry-is-browser-safe` follows every reachable import. It also starts at app feature indexes and the feature registry, read-model contract.ts files and ways-in/*/endpoints.ts. Installed contract trust is explicit; built domain, application and identity contract doors are trusted. No computed production imports may hide an edge.
- A name ending in Testing is for tests and testing code whose runtime exports all end in Testing. Path re-exports preserve that name. Production never imports tests. Tests sit directly inside a tests/ folder in the folder they test. A package's tests use its public entry; only adapter-local tests import adapter production files directly. Other tests may use adapters/tests support, not adapters themselves.
- Each Effect workspace has its own tsconfig extending the root base and its own typecheck/test scripts. Rules is plain JavaScript, has no tsconfig, and checks each source with node --check. Its own layout and comment-rule exemptions stay.
- Every framework package an app mounts ships its short AGENTS.md in files. It documents mounting, options, ports, migrations and fixed rules. Keep it in step with the package API.
- Ten public packages publish only through `.github/workflows/publish.yml`: rules, domain, application, auth-jwt, identity, party, migrations, call-audit, comments, node-host. Never publish by hand. The TypeScript packages build to dist but use src in this workspace. A release bumps a package and every workspace pin together, with approval. Publish tags come only from pnpm-publish-summary.json and use GITHUB_TOKEN so tags cannot retrigger publishing.

## App folders and import directions

```text
src/
  features/index.ts  Features registry
  features/<name>/    index.ts with one feature and handler + tests/
  read-models/<name>/  index.ts + optional contract.ts + subjects + Postgres adapter
  ways-in/<name>/      way, endpoints.ts, wording overrides, optional page
  composition/        modules.ts, sign-in.ts, access.ts, app.ts and tests/
  main.ts             Host and root/way join
  index.ts            optional
```

The composition filenames above are a review rule, not a lint requirement. `ways-in/hooks/`, `ways-in/schedules/` and `ways-in/events/` are system ways, not new app areas. They have no network path. `app-folders` checks these areas. `layout({ layers })` accepts only features, readModels, waysIn and composition as area keys. There are no old layer aliases. A Next host keeps src/app as its way-in area through waysInLayer. `host: "next"` also owns proxy.ts, instrumentation.ts, next-env.d.ts, .next output and the shell-free global-error page. The design and TypeScript host presets keep their existing exemptions. Generic main/index defaults do not become Next entry files unless named.

- `feature-file` requires exactly one `defineFeature` call in each feature index, exported as a direct const value. Its folder contains only index.ts and tests/. Type exports are allowed; tests are exempt. Import the builder by name from application/contract; import renames are allowed, namespace and runtime aliases are not. Feature imports allow only effect, kit/package contract doors and same-app read-model contracts, never other feature indexes. The handler only calls declared edges through call, never module services. The whole dependency tree stays browser-safe.
- `features/index.ts` exports only the Features object from named feature imports. Built-in roles and the system permission list live in composition. Feature re-exports and type exports are allowed; no calls, spreads, computed members or stray values. ESLint feature rules use literal features/, not custom layout areas.
- Features may import package and kit contract doors and read-model contracts, never other features, ways or composition. Features never call features; reusable work is a module operation. `feature-file` rejects feature-to-feature imports. Runtime/composition acquisition rejects feature targets with typed GraphInvalid; validatePlan reports them at the exact edge path. Feature-folder cycles fail even when no individual files form a cycle.
- Read models import packages and kits, not other app areas. Their index.ts and optional contract.ts are the only outside doors.
- Ways may import values only from the kits, effect, package ./contract doors, the app's features and composition, and their own way folder. Only ways-in/<name>/page/** may also import third-party npm values, never workspace mains, @house-rules mains outside the kits, Node builtins, SQL or platform adapters. Other package main entries and read-model doors allow only type-only imports. Ways never import other ways.
- Composition may import features, read-model doors, packages and kits, never ways. main.ts joins root and ways by passing way values or a factory into the root. The root does not import ways to get that value.
- No file or folder is named utils, helpers or misc. No import cycles or deep package imports.

## Features, operations and execution

A feature is an exposed entry point for one thing the app lets a person or the system do. Every feature must be exposed on an HTTP, MCP, hook, schedule or event way; there are no internal features. Its index.ts calls defineFeature once with schemas for input, output and failure, a description, optional title, permission (resource:action or explicit null), edges, literal flags, optional start and handler. Features never call features; their edges target operations only. A short sequence used by exactly one feature may stay in that feature's edges. Move it to a process module when a second feature needs it or it gains state. Person is the default start; hooks, schedules, events and public features declare a system start with reason and startedBy.

An operation is one thing a module or read model can do. Declare it with defineOperation and export descriptors from ./contract as <Module>Operations. Bind its handler with bindOperation in a service-capturing binder wired in composition. Features need no separate binding.

A module owns a capability or a process, with or without state. A capability module owns state, a computation or an outside effect and its rules. A process module sequences capability operations and may call other process modules without cycles. Capability modules never call process modules. Invariants stay with the capability that owns the data or computation. A computation takes inputs as data; fetching those inputs from other modules belongs in a feature or process module.

The module owns each event fact: declare its schema in ./contract and return the fact with the operation result, including the before and after state it alone knows. Capability modules never emit, depend on event-log or read CurrentActor. The composing feature or process operation chooses which returned facts to record, through a declared edge to EventLog.record in the same unit as the writes. Not every write must become an event. The record binding stamps the envelope from the caller, clock and request; system callers have no person actor. Never rebuild a module fact in a feature or process module. Facts about the whole flow belong in an app-owned package contract. An app that records every write may exempt personal UI state such as notification read markers, preferences, quiet hours or time zone.

A plain edge keeps the caller. asSystem(target, reason) switches downward to SystemCaller with a nonblank reason, never back to person. Builders and asSystem construct without throwing. No location marker or invented feature permission.

```text
way in -> feature -> declared edges -> operations -> module services and data
                                      read operations -> published views
composition: choose adapters, bind operations, plug sockets, acquire Runtime
```

Call `defineOperation`, `bindOperation`, `defineFeature`, `defineWay` and `endpoint` directly through named imports from their owning kit doors. Import renames are allowed; namespaces, destructuring, runtime aliases, builder barrels, value/callback passing and dynamic builder imports are forbidden. Non-kit production workspace packages may not import defineFeature, defineWay or endpoint, even unused. They may import defineOperation and bindOperation directly for descriptors and service-capturing binders. Non-kit production code cannot re-export any kit builder, including bindOperation, under any name or star export. Finished descriptors and binders are values, not builders; public doors and app mounts such as bindComments(service) and bindParty(service) are allowed. Domain/application kit implementations, tests and top-level tooling are exempt. CommonJS require/createRequire of kit doors or builder-bearing relative/workspace sources and nonliteral require fail closed. Package-helper namespace, import = and default member calls follow builder identity too. Only real configured domain/application kit roots with matching package names are exempt, never a nested package.json. Kit named/star re-export files retain builder identity through relative and workspace doors. Unrelated APIs, including third-party endpoint imports, renames and re-exports, are not kit builders. Production app src and Effect workspace-package src, including both kits, are ESM-only: no require, module.require or node:module/module createRequire loading. Rules, tests and tooling outside src are outside that blanket ban; narrow builder-origin checks still apply to other production packages. Test exemptions are relative to the owning src, never a workspace named test/tests. `feature-builders` permits defineFeature only in a feature index and forbids operation builders in features, including the registry. Ways, including hooks, schedules and events, accept Feature values only, never operations. Hooks, schedules, events and public features declare a system start with reason and startedBy. Hook ways name one caller-owned slot and one system feature, plus explicit Mean, input and failure mapping. Composition installs slots after Runtime, capturing Runtime, StepTrace, UnitOfWork and CallWatch. Calls use Effect-returning runFeature with May.system, the gate policy, a fresh request id and hook:<name> channel. They never call Who or inherit CurrentActor or MCP context. Duplicate slot providers fail GraphInvalid. Schedule ways name a UTC cron and selector/item system features; the selector returns an array of item inputs. Composition validates cron at acquisition, then forks scoped drivers after hooks. They wait for the next tick, never run at startup or catch up missed ticks, and process items sequentially through runFeature, one unit per transactional item. Item failures are logged and processing continues. Disposal stops drivers before resources close. There is no distributed lease; item operations must be idempotent. Every system way states Mean. Trusted provisioning and nightly maintenance use Mean.allow; other system ways use Mean.no unless the owner approves otherwise.

A feature lifts readOnly with AND, and transactional, destructive and needsApproval with OR across its graph. Literal flags stay literal. Its person closure stops at system edges; its system closure includes every permission below them. System starts place all permissions in the system closure.

Execution runs CallWatch once, checks exposed feature identity, checks person then system closures, asks Approval once if lifted, and opens one unit if transactional. Inner calls use only declared edges and add trace steps; they repeat none of those feature gates. Every inner call rechecks its own permission against the permissions loaded at feature start. Process operation edges run under that same feature, with no new gates, approval or unit, and every inner call traced. Object policy stays inside the module and takes an explicit Actor. Outside effects stay per item inside a system feature's unit, through a process operation such as Delivery.sendDue; they never move into the original producer feature's unit.

`Runtime.layer({ mounts, features, ways })` reads mount services and calls their binders once. It and composition reject duplicate service keys, operation identities or names, missing/extra/duplicate mount bindings, cycles, invalid system reasons and duplicate exposures with typed GraphInvalid. Bindings capture long-lived module services. Only CallerContext may remain as a per-request handler requirement. Person execution installs CurrentActor from the same Actor; system execution cannot inherit person authority.

The root owns `composition({ modules: ModulePlan, features, ways, may, system })`. A package main exports a plain `<Module>Mount` with service, operations and binder; read models export theirs from index. Only composition/modules.ts chooses mount layers. Features and contract doors never import mounts. May is an Effect resolving a MaySocket after modules are built. It plugs one app-level May from Party. Operations declare permissions in code; Runtime.permissions is their catalogue. Party stores people, organisations, relationships, custom roles and assignments. A person may define or assign a built-in or custom role only if they hold every granted permission in that same scope; system assignment is exempt. `party:admin` alone grants no extra delegation rights. Org-scoped role reads expose only global built-ins and their own organisations' custom roles. Revoking roles, deleting roles and removing relationships need approval. Composition declares built-in roles and the explicit system permission list. That list is the system's authority, not the event author's roles. Every system permission grant is an owner decision, visible in the plan review. At feature start, the role check requires every permission in the closure and fails 403. Inside the operation, the relation check protects the loaded object in the same unit as the write; lists filter relations in SQL. An agent is the user and holds the same roles. MCP narrows access only through read-feature exposure. Adapter selection happens only in the app's composition modules file, from config; main.ts, ways, features and tests get one modules layer and never name an adapter. Derive the kit-owned PermissionCatalogue from mounts; acquire modules and infrastructure in one memoization scope; capture mount bindings once; acquire Runtime and May; install hook slots; then start scoped schedule and event drivers. Runtime.permissions exposes that same catalogue array. The router from toFetchHandler owns dispatch, endpoints, MCP toolkit and metadata paths. Do not hand-build Tool.make, Rpc.make or HttpApiEndpoint calls outside application. Dispose the router before the composition. Lazy build retries, scoped sharing, interruption and final disposal stay intact.

## Inside a module

- Domain modules are packages, including app-owned domain modules. There are no folder modules. A package src/ holds only index.ts, facade.ts, storage.ts, optional contract.ts, adapters/, tests/ and subject folders. Migrations sit beside that code in the owning module's migrations/ directory.
- Declare one root service with `defineModule<Self, Shape>()(id, { make })` in facade.ts. Its methods return Effects with no requirements. Capture long-lived ports, never CurrentActor, CallerContext or any PerRequest service. An Effect make gives layer; an options make gives layer(options). Presets are data and adapter statics stay in the class. Effect owns lazy build, memoization and scope. No global caches or registries.
- Declare each module's role as capability or process in plans and mount map metadata. Plans reject capability-to-process operation edges, plain or system. Process modules may be stateless sequences or durable sagas; state does not decide the role.
- Cut modules by consistency, access and life cycle, not one noun per module. Keep dependent children together when writes, SQL access guards and deletion cascades share a boundary. A thing with its own life becomes another module.
- Use subject folders even for one subject. Name files after what they own, not types, models, schemas, drafts, errors, validate, validation, constants, interfaces or internal, in any letter case. Subjects import each other in one direction. Subject-folder cycles exclude tests, adapters and root files. Subjects never import their own index, facade or contract barrel; storage.ts remains importable.
- Only index.ts, facade.ts and adapters import their own adapter production code. Tests outside adapters may import adapters/tests support only. Adapters mirror subjects as adapters/<kind>/<subject>.ts; this naming is a review rule.
- Each Context.Service gets one file. Non-root service layers are static Layer.effect members beside their service. Storage-port implementations live in adapters.

## Modules own data; read models consume views

- A module owns its migrations, tables and views. CREATE VIEW publishes a view over only that module's own tables/views. SQL never names another module's tables/views; ask its service instead. No cross-module foreign keys. Keep foreign ids as plain columns.
- A storage port answers facts, not permissions, standing or limits. Domain code owns those decisions. Only adapters and named adapter packages import effect/sql, @effect/sql-* or @effect/platform-*. The fence stays error severity. No ORM or query builder. Write plain SqlClient SQL, decode rows with Schema, and test Postgres against a real database through MigrationsTesting.database, never a mock.
- Stored modules ship memory and Postgres adapters plus a shared store suite against both. Domain tests may use memory only. Memory registers undo with UnitOfWork.onRollback before changing state; Postgres joins the open transaction. Writes call UnitOfWork.required and fail NoOpenUnit outside a live unit. Modules never open a unit.
- Only the feature runtime and kit-owned event driver open production units. Production app code, including feature handlers, read models and composition, never calls UnitOfWork.atomic. Feature transactions span every module write in the graph. A transactional feature treats unexpected NoOpenUnit as a defect; a plain feature keeps it typed. Tests and tooling outside src may open a unit explicitly: repository-root scripts/ or the workspace's own top-level scripts/ beside package.json. Production src/scripts, module scripts and feature scripts have no exception. Kit runtime and unit adapters implement units. Background work enters a system feature through composition's system ways, one unit per item or delivered event. The event driver owns claim and settlement units; app code and modules never open them.
- Each migration-list item accepts exactly one nonempty workspace or package key. Folder locations are rejected. The package's real identity is unique across locations and names. Every location kind's migrations directory must not be a symlink or resolve outside its real owning module. Normal workspace and installed-package module-root symlinks remain valid; validate migrations against that resolved root. SQL migration files themselves must not be symlinks, even to targets inside the owner. Name defaults to the slugged basename, history table to <name>_migrations. Existing name/table uniqueness and adopt {from,ids,rehash?} rules apply to every location kind. Installed packages declare houseRules.migrations and ship it. Workspace migrations remain in migrations/. The runner applies the whole list atomically and only reads old adoption history. Runner and checker mirror a private canonical breakpoint split before SQL lexing, with one shared fixture. Breakpoint lines are reserved even inside quotes/comments; the pinned driver requires one command per chunk. The runner's first transaction statement and the statement before every migration chunk are SET LOCAL standard_conforming_strings = on. Module migration and read-model SQL forbid the case-insensitive whole words standard_conforming_strings, backslash_quote, set_config and pg_settings anywhere, including literals, comments and dollar bodies. Unrelated JavaScript prose and the runner's internal pin are outside this guard.
- Register every module with migrations in migrations.json. Modules own SQL as packages; read-model SQL selects their published views. The checker preserves raw transaction checks and bans production module/app UnitOfWork.atomic calls. Test SQL is allowed only under the owning workspace's fixtures/ or tests/ folders. Applied migrations are append-only; never edit, rename or remove one.
- A read model has no migrations and no required memory adapter. Its Postgres SQL is exactly one static SELECT or WITH...SELECT over known published views, never tables, schema-qualified relations, writes, unknown names, SQL functions or raw/dynamic fragments. Use the checker's documented bounded grammar; unsupported SQL fails rather than being guessed. Read-model SQL and the view-DDL ownership scan reject non-ASCII outside strings or quoted identifiers, including comments; Unicode-escaped identifier values are unsupported. Plain/N SQL strings with backslashes fail in read models and the view-DDL ownership scan; use E strings or dollar quotes. Only parameter values may interpolate. Unreadable source fails closed. Without a database, wire a named read-unavailable port with an unavailable error. Person filtering stays in SQL and needs an A/B privacy test.

Limits: the checker does not semantically analyse PL/pgSQL, DO bodies or dynamic EXECUTE. Their ownership is a review rule. The legacy table-ownership scan uses the shared PostgreSQL lexer and blanks ordinary strings. Dollar bodies get a best-effort nested lexical scan, with raw body text as fallback when body lexing fails. A SELECT-only database role granted access to published views is a planned follow-up, not implemented in phase 1.

## Effect and errors

Before editing Effect code, read the installed effect/AGENTS.md and relevant ai-docs under a workspace node_modules, then the source mirror `.agent_sources/github.com/Effect-TS/effect`. There is no root Effect install. Trust pinned stable 4.0.3 over memory. Use the house-rules skill for app/module work and the live package guides for final APIs.

- Expected failures are Schema.TaggedError classes in the error channel, never global Error or throw inside Effect code. Every feature or operation failure member declares `kind: errorKind(...)`: not_found, conflict, forbidden, unavailable or invalid. Schema.Never is valid.
- Application maps kinds to fixed status/code pairs: 404, 409, 403, 503 and 400. Module user-facing errors retain their message; unavailable and plumbing messages must be fixed text. Keep cause, permissions, reasons and driver text in internal values/logs, never public message fields. Defects use generic 500 internal_error.
- WordingOverrides in a way's folder change message only. No status, code, headers, response body or actor-aware mapper. Composition holds no views table. Gate, unit, SQL, graph, call and closed-composition failures get fixed public text; overrides run on top.
- Tests use it.effect or it.layer from @effect/vitest. Never Effect.run* or ManagedRuntime.make in tests; only application entry points run Effects.
- Pin all Effect runtime packages together, including direct @effect/platform-node-shared wherever platform-node is installed. @effect/tsgo versions separately. Never lower diagnostics below error, override the Effect plugins block, or weaken a hook to pass.

## Ways, web and agent access

The host's startup-fixed `/healthz` and `/readyz` paths (or their configured replacements) are approved non-feature public paths alongside MCP protected-resource metadata and static page files; the host probes bypass Who, May, audit, units and trace.

Feature handlers and inner operations never receive credential headers (Authorization, Cookie, Proxy-Authorization, Set-Cookie) on any way; only transport, Who, CSRF and session handling see them. Hooks, schedules and events run on a fresh context built only from composition-captured Runtime, StepTrace, UnitOfWork, CallWatch, the way's Approval, CallPermissions from May.system and CallChannel. Each execution adds a fresh request id, fresh log annotations and a new root span. Caller-provided services, annotations, spans and network request context are not inherited.

HTTP/MCP `defineWay` names protocol, path, features, Who, Mean and optional message overrides. An HTTP way lists public features in `public`; each must also be in `features` and declare a system start. Only those requests skip Who, ignoring any token, and use composition's system permissions. MCP refuses `public`. Ways carry no permission lists and no May plug. HTTP uses browser-safe `endpoint(feature, at?, options?)` descriptors and defineApi. Export client endpoints from ways-in/<name>/endpoints.ts. Clients use application/contract and module contract doors, never bindings. Page/API may share one service with Node Host staticFiles, or use a separate origin with explicit CORS and a client baseUrl. CORS is not access control. Cookie writes still require CSRF, including session issuance before a cookie exists. Session issue accepts a Struct or Union of Structs with at least one token/expiresAt member. Only a token-bearing value sets a cookie; every member's body omits token. A tokenless value returns 200 without a cookie.

An event handler is system-started and author-caused. Use EventInput from application/contract: `{ event: EventEnvelope, causedBy: string | null }`. causedBy copies the stored actorId and stays data in input and trace, never an Actor, permission or authority. Do not query or snapshot the author's roles for delivery; revocation cannot change the system's grants. Events without an author carry null. Audit attributes the execution to the system. If a side effect must be checked against the person who acted, keep it in that person's feature and unit. If it may run later, the system performs the reaction with its own explicit permissions and records the author as the cause. Normal person reads keep hiding other people's objects and refusing system callers where specified. Reactions needing person-owned data use separate system-only read operations with their own permissions, such as WorkItems.getForSystem with work_items:system-read; never weaken person reads or impersonate causedBy.

Declare event ways in ways-in/events/ with `defineWay({ protocol: "event", name, on: [kinds], feature, mean })`: one system-start feature per consumer, explicit reason and startedBy, and Mean.no unless the owner approves otherwise. No path, Who, public or MCP fields. The way name is the consumer name. Its distinct nonblank on kinds must exactly equal that consumer's kinds, never a subset or superset. Acquisition rejects missing/extra kinds with named differences, duplicate consumers, missing EventSource or person starts with GraphInvalid.

Application owns the caller-owned EventSource port and never imports event-log. EventLog.source fills it; mount the plug beside EventLog with Layer.provideMerge in composition/modules.ts. Consumer config contains name, kinds and retry policy, not a handler. Removing event-log, its source plug and event ways must leave the rest building and passing. Composition starts one scoped driver per event way after hooks. It commits a due claim in its own unit before delivery, then takes the event, calls runFeature as system with event and causedBy, and settles success in one unit per event. Transactional features join that unit. Failure rolls it back; failure bookkeeping uses a separate unit and a fixed safe summary. The committed attempt survives for backoff and eventual dead-lettering. Source wakes plus a periodic sweep drive delivery; composition.eventSweepMs is a positive integer, default 30000. Startup drains source-reported due work only. Retries run on the next wake or sweep at or after the source's retry deadline, not necessarily at that deadline. Executions use May.system, a fresh request id, event:<way> channel and a new root span. Disposal stops drivers before resources close. Delivery is at least once; handlers must be idempotent. Cursor locks serialize one consumer's handler unit; there is no distributed lease.

A Node Host call lives in main.ts, uses @house-rules/node-host and a plain fetch handler, never node:http in Effect app code. Next already has a Host. Preserve session token omission, exact origin checks, request ids, failure-code opt-in, codecs and disposal. `call(app, feature, input, incoming, {way, admitted?})` selects a named way and uses Mean.allow. Opaque admitted state stays within one request, composition and way, never cached beyond token validity.

- The agent gets the same module access as the user. Every exposed tool needs an A/B access test under a fake actor. Tools call app features, never services or databases directly. Tool output is structured data; user text never carries model instructions.
- Start with read-only MCP tools. Write/destructive tools, token scopes and owner-only tools need named owner approval. Hard-to-undo actions set needsApproval. Keep catalogues small, with summary/read splits for large records.
- MCP tool definitions belong to ways and are built by the router from features, descriptions and lifted flags. Tools add title, idempotent and openWorld hints. Prefer pinned Effect McpServer/Tool/Toolkit over a new library.
- Mean.elicitation asks the human. Decline, cancel, no, missing support and failed elicitation fail closed. An agent never supplies its own approval.
