# v2 decisions

The ledger of what the owner has decided about the v2 shape, and what is still open. The spike spec is `docs/v2-spec.md`. The built spike is `examples/booking-v2/`.

## Decided

1. **Move forward.** v2 replaces today's shape. No backward compatibility, no old stuff kept alongside.
2. **Names.** These words carry the model: node, edge, caller context, entry, socket, plug, way in, link, module, read module.
3. **Sockets.** A socket is a level above the Effect slots: a question every app answers. A plug answers it as one bundle.
4. **One node type.** Capability, feature and use-case merge into one node. A node's place is a folder, not a type.
5. **The graph is the feature registry.** It is generated from the code, and a PR shows its diff.
6. **A module is a boundary.** Your own modules are folders. Shared modules are packages.
7. **Misuse is stopped by visibility, not rules.** Other paths, such as a partner booking without payment, are legitimate. (Decision 51 removed the partner way; the principle stands.)
8. **Read modules over published views.** They query the database directly, joining only views other modules publish. There is no second store.
9. **Caller context, not system nodes.** A call runs as a Person or as the System. A node switches to the system for one edge, with a reason.
10. **Two AGENTS.md rules change** together with their checks (see `TODO.md`).
11. **The spike** lives in `examples/booking-v2` on `task/accounts-example`. MCP stays read-only. The read-view exception applies to the spike only.
12. **Read unavailable.** Without `DATABASE_URL`, the read module answers 503 through a named port. It is not a memory adapter.

13. **Kit into the framework (K).** Nodes, edges, caller context, entries, closures, registry, sockets/plugs and step trace move into the framework kits. `implement` becomes node-aware. The `entryContract`/`entryHandler` wrapper, the synthetic `entry:<name>` permission and the `marker` field disappear.
14. **App nodes in the app (A, X).** A node rule replaces the use-case rule: `apps/<app>/src/nodes/` holds one node per file; nodes may call nodes without cycles; a way in exposes only nodes from that folder. The app-nodes package disappears.
15. **Modules as folders** inside `apps/<app>/src/modules/<name>/`, with the same boundary checks a package gets. Packages are for shared modules only.
16. **Read models (R).** The concept is "read model". One `read-models` folder, one read model per screen (`MyBookings`). The migrations check learns published views; a read model only SELECTs from published views, never a private table, never writes. The spike-only exception ends.
17. **Views (V).** Module errors declare a kind (`not_found`, `conflict`, `forbidden`, `unavailable`, `invalid`). The kit maps kind to status by default. Views move into each way in and hold only wording overrides. Kit and plugs map plumbing errors themselves.
18. **Grant scope (G).** A way in's closure check accepts only the entries that way in exposes.
19. **Destructive lifts (F)** from the graph to the entry, the way approval does.
20. **Caller-context details (P1)** stay as the spike built them: the system's own list, a required reason, system mode inherited downward, two closures.
21. **Law and docs** (`AGENTS.md`, `CONTEXT.md`, README, skill, site) are rewritten in v2 words, together with the checks that enforce them.
22. **One example.** `booking-v2` becomes the example: no `v2-` prefixes, no spike framing.
23. **Delete the old stuff (M).** Approved: `examples/booking-platform/` whole (owner's uncommitted web work backed up at `~/.local/state/v2-spike/backup-booking-platform-uncommitted/`), its two `migrations.json` entries, and `packages/rules/src/use-case-is-capability.mjs` with its tests. Further v1-only framework files are listed by exact path for the owner before deletion. `.pi/specs/*` stays as history.
24. **Breaking changes to the public npm packages** are approved; a new version will be released later, with the owner's yes at release time.
25. **Domain modules are packages again** (2026-10-19, replaces 6 and 15). Every domain module is a package, such as `examples/booking/packages/bookings` and `packages/billing`. A part that only makes sense inside one module is a subject folder in that package, not a module of its own. The app holds no `modules/` area, and the rules drop folder-module support: the `modules/` area, `folder` entries in `migrations.json`, and the folder-module door and cycle checks.
26. **App nodes live in `features/`** (2026-10-19). App nodes are the features, the old use-cases. Their folder is `apps/<app>/src/features/<name>/` with `node.ts`, `entry.ts` and `handler.ts`. `defineNode` and the word "node" stay as the technical name for one step in the graph.
27. **Read models stay in the app** (2026-10-19) at `apps/<app>/src/read-models/<name>/`. A read model is one SELECT over published views for one screen, so it is app code, not domain.
28. **Ways import contracts, not domain values** (2026-10-20). A file in `ways-in/` may import values only from the kits, `effect`, any package's `./contract` door, `features/`, `composition/` and its own way folder. From a package's main entry it may import types only. Plugs such as `Identity.who` are built in `composition/` and passed in. This restores the fence that folder modules had.
29. **`examples/rejected-shapes/` is removed** (2026-10-20). The rules' failing fixtures and the rules page cover each shape; the untested v1 snippets go.
30. **Prose and placement rows need no test** (2026-10-20). A reference VERIFICATION.md row that claims only prose (what a README says) or file placement (which file holds a wiring line) is N/A for acceptance item 3. `examples/booking/TESTS.md` lists each such row and where to look. Behavior rows still need an executable test.
31. **Adapters are chosen once, in `composition/modules.ts`** (2026-10-20). The app's composition exports one modules layer. It reads `STORAGE=memory|postgres` (declared in `.env.schema`, default memory; `DATABASE_URL` required only for postgres) and wires every module's adapters, the unit of work and the database client itself. `main.ts`, ways, features and tests get that one layer and never name an adapter. Tests pick Postgres through config. Non-storage test doubles, such as a fake payment provider or an audit log to inspect, stay as explicit options. The packages' own store suites still run both adapters directly. This is a review rule in `AGENTS.md`, not a lint check. (Changed by 48 and 49: `modules.ts` now exports `modulePlan()`, one mount per module plus the infrastructure layer.)
32. **One file per feature, one builder** (2026-10-21). A feature is `apps/<app>/src/features/<name>/index.ts` (plus `tests/`). It exports exactly one `defineFeature(name, { description, title?, permission, input, output, failure, edges, flags, start?, handler })`. The handler only calls declared edges through `call`, so the file stays browser-safe. A feature is its own entry: `defineEntry`, `entry.ts`, `node.ts` and `handler.ts` go away for features. `start` defaults to a person call; hooks and schedules declare a system start with a reason.
33. **`features/index.ts` is the feature registry** (2026-10-21). It re-exports every feature as one `Features` object and holds the permission lists (member, partner, agent, system). It replaces `composition/entries.ts`. (Changed by 40 and 48: the permission lists left; built-in roles and system permissions live in `composition/access.ts`.)
34. **Module operations are "operations"** (2026-10-21). Modules use `defineOperation` and `bindOperation`; a module exports its descriptors as `<Module>Operations` from its `./contract` door. Bindings still capture services in composition.
35. **The word "node" leaves the API** (2026-10-21). Public API, types, rules, presets and docs use feature and operation: for example `Runtime` instead of `NodeRuntime`, a `feature-file` rule instead of `node-file`, `configs.features` instead of `configs.nodes`. "Edge" and "graph" stay as the words for links. No aliases. Ways, May lists, hooks and schedules accept only `Feature` values, so a module operation cannot be exposed.
36. **Two access checks, two layers** (2026-10-21). The role check is application: the gate at feature start asks whether the caller holds every permission in the feature's closure. It needs no object and fails 403. The relation check is domain: inside the module's operation, on the loaded object, in the same unit as the write. It may fail as not_found so it reveals nothing. Lists filter by relation in SQL.
37. **Permissions live with operations, in code** (2026-10-21). Each operation declares its `resource:action` permission. The runtime exposes the app's permission catalogue: every permission its operations declare. Nothing outside code invents a permission.
38. **Party owns who is who and who may do what** (2026-10-21). Party grows from persons to the Party model: organisations, relationships between parties (for example staff of, partner of), roles (a name plus permissions) and role assignments (a person holds a role, globally or within one organisation). All of it is stored in party's own tables, with memory and Postgres adapters. Identity stays narrow: a login maps to an ActorId, and it never learns roles.
39. **Built-in roles in code, custom roles in the database** (2026-10-21). An app declares its built-in roles and their permissions in composition. Custom roles are created at runtime through party operations, and their permissions must come from the catalogue. Managing roles needs `party:admin`, and the destructive operations need approval. A permission that is in the database but no longer in the catalogue is ignored by the gate.
40. **One app-level May plug, from party** (2026-10-21). Composition plugs `Party.may(...)` once. For a person caller it answers with the union of the permissions of all roles the person holds, in any context. Ways no longer carry permission lists. A way names its Who and the features it exposes, and that exposure is its only narrowing. System callers keep their system permission list, declared in composition.
41. **The agent is the user** (2026-10-21). An MCP caller gets the same roles and permissions as the person behind the token. MCP stays read-only because it only exposes read features. The `agent` permission list is removed. A token scope that narrows access further is a later addition, not part of this change.
42. **Relations between parties are asked of party** (2026-10-21). When a module's relation check needs a fact about parties, such as whether a person is staff of an organisation, it calls a party operation through a declared edge. The module still owns its own object relations, such as a booking's owner.
43. **No privilege escalation** (2026-10-21). A person caller may define, grant or assign a role only when they hold every permission of that role, in the same scope. `party:admin` alone grants nothing beyond what its holder already has. A system caller, such as first sign-in, is exempt. Org-scoped admins see and manage only their own organisation's custom roles and the global built-in roles. Revoking a role and removing a relationship are destructive and need approval, like deleting a role.
44. **The example has a web page and real sign-in** (2026-10-22, replaces migration spec section 5, "The example has no web page"). `examples/booking/apps/api` serves a Vite, React and shadcn dashboard from `ways-in/web/page/`, on the same origin through Node Host `staticFiles`. A side menu shows each module as a plug that composes the app: accounts, bookings, billing, party (people, organisations, roles), the audit trail and the app's registry of features, permissions and ways. Every call shows its status, error code and request id. Sign-in is real: an app-owned `@example/accounts` package (email and password, PBKDF2, ES256 tokens the app signs), brought back from v1 in v2 shape. The web way uses the application kit's session cookie with CSRF. `scripts/migrate.ts` applies `migrations.json`. Dependencies return at v1's exact pins, with the owner's yes.
45. **Public features are system starts a way opts into** (2026-10-22). A feature that runs before anyone is signed in, such as sign-up or sign-in, declares a system start with a reason, like a hook. An HTTP way lists such features in `public`; for those the router skips Who and runs the feature as a SystemCaller. The caller stays person or system: there is no anonymous caller. A public feature's permissions come from composition's system list. An MCP way refuses `public`. A way may not list a person-start feature as public.
46. **A session can come from a union output** (2026-10-22). A failed sign-in must commit its attempt count, so `sign_in` returns `SignedIn { token, expiresAt } | InvalidCredentials` as data, and its unit commits. A session-issue route accepts a union output in which at least one member carries `token` and `expiresAt`. It sets the cookie only when the value carries a token, and the body never carries the token. A refusal is a 200 answer the page shows. A failure still rolls back everywhere.
47. **Identity is one configurable concept with providers** (2026-10-22, changes 38 and 44). `@house-rules/identity` answers "how does a person prove who they are". It keeps the login bindings, `(issuer, subject)` to ActorId, and gains providers chosen in composition: `oidc` for an outside issuer such as Clerk, verified through auth-jwt, and `passwords` for the app's own email and password sign-in, which signs ES256 tokens and publishes its keys. One identity config pairs the issuer and its verifier, so they cannot drift. The passwords provider lives in its own subject folder with its own tables. An app that never uses it carries those empty tables. auth-jwt stays a separate plug, a pure token checker that MCP also uses. Identity still never learns roles; party owns them. The example uses the passwords provider instead of an app-owned accounts package.
48. **Composition answers four questions, each once** (2026-10-22). An app's `composition/` holds about four files: which modules (one mount entry per module, giving its layer per storage, its binder and its operations), how people sign in (every identity provider and each way's Who, including the MCP issuer and dev-only local issuers), who may do what (built-in roles, system permissions, the May plug and the permission catalogue), and how the app starts (`createApp` and its config). A module is listed once; the Runtime bindings and the registry both come from that list. The registry is generated from the running app's real features and ways, never from hand-written lists. Hooks and schedules are system ways in `ways-in/`, beside web and MCP: a hook names the slot that triggers it, and a schedule names a real clock that composition runs inside its scope. The kit gives the mount shape and the system ways; the exact API is designed first and shown to the owner before it is built.
49. **Decision 48's design choices** (2026-10-22, owner chose each; design at `~/.local/state/v2-migration/compose/design.md`).
    1. A module exposes a plain `<Module>Mount` value (`{ service, operations, bind }`) from its main door; read models export theirs from their index door. There is no mount builder.
    2. `PermissionCatalogue` moves to the application kit. The kit fills it from the mounts' operations before any module is built.
    3. The registry is `registry(app)`, a snapshot of the validated running app, plus a pure `renderRegistry(snapshot)`.
    4. A schedule clock is a UTC cron. It first runs at the next tick, handles items one by one, never catches up missed ticks, and has no multi-process lease yet, so scheduled item operations must be idempotent.
    5. Nightly billing cleanup becomes a read-only selector of due payments plus an idempotent expire-one feature, with one unit per item.
    6. Dev and test token issuers become an `Identity.devLocal({ issuer })` provider that refuses production. Tests get a signing handle through `composition/sign-in.ts`, never through ways.
    7. Each system way states its Mean. The new-login hook and the nightly schedule use `Mean.allow`; any other system way uses `Mean.no` unless the owner approves otherwise.
50. **Feature code never sees credentials or caller leftovers** (2026-10-23, owner chose both).
    1. On every network way, HTTP and MCP, feature handlers and their operations never receive credential headers: `Authorization`, `Cookie`, `Proxy-Authorization` and `Set-Cookie`. One kit sanitiser applies where execution starts. Only transport, Who, CSRF and session handling see the full request.
    2. Hooks and schedules run on an allowlist. Composition captures only what feature execution needs, after Runtime: Runtime, StepTrace, UnitOfWork, CallWatch, Approval, system permissions from `May.system`, and CallChannel. Each call gets a fresh request id, fresh log annotations and a new root span. Nothing from the caller's fiber carries over, even when a hook fires inside a person's sign-in.
    3. Temporary signing keys, such as `Identity.devLocal` and the passwords provider's ephemeral key, sign only when `NODE_ENV`, trimmed and lowercased, is exactly `development` or `test`. Any other value refuses, including a missing one.
51. **The partner way is removed** (2026-10-23, owner). The booking example drops `ways-in/partner/`, the `book_for_partner` feature and the partner `Identity.devLocal` issuer. It was a dev-only demo with no real caller. The web way still has a `devLocal` test issuer, so the reference app still refuses to start in production. Every new login now gets `member`. The built-in `partner` role stays, held by the seed user bob, as an example of a narrower role on the web way.
52. **The booking example starts in production, and local signing guards itself** (2026-10-23, owner). In production the example signs in only through `Identity.passwords` with `ACCOUNTS_SIGNING_KEY`, plus the optional `Identity.oidc` MCP issuer. A missing key refuses startup with a typed error. `Identity.devLocal` and its test signing handles are wired only in development and test. `AuthJwtLocal.make` and `.layer` refuse on their own unless `NODE_ENV`, trimmed and lowercased, is `development` or `test`. One check, `requireDevelopmentSigning` from `@house-rules/auth-jwt`, serves `AuthJwtLocal`, `Identity.devLocal` and the passwords provider's temporary key.
53. **Modules own their adapters; the app wires them** (2026-10-23, owner; closes P4). A stored module package defines its storage port (`storage.ts`) and its adapters (memory and Postgres, under `adapters/`), with one shared store suite run against both. Only the app's `composition/modules.ts` chooses which adapter to plug in. Storage stays inside the domain module; this is the rule already in `AGENTS.md`.
54. **One gate policy: feature gate plus recheck** (2026-10-23, owner; closes P2). The gate at feature start checks every permission in the closure. Each inner call through a declared edge then rechecks its own permission against the permissions loaded at start. `featureOnly` and the `gatePolicy` option are removed.
