## 1. What the page says

The page is short. It gives one tree and a few rules. In our words:

- Group code by what it is about, not by what kind of file it is. The page quotes Sam Goodwin: "src/{domain} instead of src/{mechanism}", with `src/coding/edit.ts` beating `src/tools/edit.ts`. "tools" is the "mechanism", "coding" is the "domain".
- "Keep one service and its Layer in each file." The service captures what it needs when it is built, so callers "need only that service". Request data, such as who is calling, is passed in, not captured.
- "At each entrypoint, assemble and provide Layers in a composition root." Each entrypoint gets its own root.
- "Keep platform adapters behind service ports." The domain names a job. A `platform` folder (or, in rat-stack, another package) fills it.
- Put the domain's input, output and failure schemas, its expected errors, and its optional lifecycle machine beside the behavior. Errors carry useful context, such as the failed path.
- "Mirror domain folders in tests." Tests get their services through Layers.
- A table at the end separates the Effect idiom from rat-stack's own additions: colocated `make` plus `static layer`, capability contracts, cartridges, XState lifecycles, a manual-runtime ban, a type-aware lint fence, and no prose comments.
- The page says disagreement is fine. Effect leaves folder layout to the app. One capability per file is called "potentially controversial". Monorepo against single package is "a separate" choice.

Two honest notes on the page itself. First, its tree is for "a small app". rat-stack's own repo is not laid out that way: `packages/core/src` in the clone is about 55 flat files with no domain folders, and `packages/core/test` is flat too. The domain cut there is the package (`core`, `auth`, `database`, `subscriber-delivery`). Second, the page does not say how to group code inside the three app layers we use (delivery, server, use-cases).

## 3. What we do that the page does not ask for

The page is about folders and Layers. Much of our fence is outside its scope. This is not a claim that rat-stack lacks these. It means this page does not ask for them.

1. A public entry per package, with `src/internal/` private. Checks: `packages-public-entry-only`, `packages-imported-by-name`, `tests-do-not-import-internals` (`packages/rules/README.md:47-48,55`).
2. Import fences between app layers: delivery and server never import each other, and use-cases never import delivery, server or each other (`packages/rules/README.md:49-51,58`).
3. Module-owned data: migrations and tables per package, no cross-module foreign keys, no SQL that names another module's tables, no use-case that opens a transaction (`house-rules-migrations`, `packages/rules/README.md:68`; `AGENTS.md:53-57`).
4. Access control in the contract: `permission`, `Grant`, `Approval`, the `Actor` and `Viewer` words, relations and policies (`CONTEXT.md:23-35`).
5. MCP and OAuth adapter rules, such as 401 challenge, audience check, fail-closed (`AGENTS.md:71-96`).
6. Exact pins and a release-age rule (`house-rules-pins`, `packages/rules/README.md:67`; `AGENTS.md` "Pins").
7. Strict compiler flags (15) and 31 Effect diagnostics at error (`packages/rules/README.md:60-61`).
8. Biome limits: 300-line files (warn), kebab-case file names, no `export *`, no `!` (`packages/rules/README.md:62-66`).
9. The fence against bypass: lefthook, `--no-verify` blocked in both harnesses (`README.md:84-95`).
10. Design-token lint for CSS and TS, and a broken-relative-link check in Markdown (`packages/rules/README.md:37-41`).
11. `no-cycles` and `production-does-not-import-tests` (`packages/rules/README.md:44,53`).

## 4. Candidate TODO items for the gaps

Written to match `TODO.md`: checkbox, bold title, one paragraph. Nothing here has been added to any TODO file.

- [ ] **Say where Layers are built.** Write one rule in `AGENTS.md`: each entrypoint has one composition root, in `src/server/` or `src/main.ts`, and that root is the only place that calls `Layer.provide` for services and slots. Use-cases and delivery handlers get a service or a slot from the root and never build one. Today `AGENTS.md:67` only says that an entry point runs Effects, and `apps/api/src/delivery/http/get-booking-route.ts:33-34` provides a `Grant` layer inside a delivery function. Give `apps/api` a small `src/main.ts` (or `server/runtime.ts`) that shows the root, the way Trippy's `apps/web/src/server/runtime.ts` does. Decide whether a layer built in delivery, like Trippy's MCP server Layer (`app/_mcp/server.ts:58-70`), is allowed. A check is hard to write here, so start with prose and the example.

- [ ] **Say how to group inside a layer.** The stack cuts apps by layer and packages by module, and `AGENTS.md:44` allows nested folders in `use-cases/`, but nothing says how to group them. Trippy groups use-cases by domain (`use-cases/trips/`, `use-cases/items/`) and delivery adapters by mechanism (`_mcp/`, `_http/`). Write that down as the default: group use-cases by the module they mostly call, keep adapters by kind. Note the side effect that is already defined: a use-case folder counts as one use-case for `use-cases-do-not-import-use-cases` (`packages/rules/docs/dependency-cruiser.md:76`), so two use-cases in `use-cases/trips/` may import each other. Decide if that is fine or if the rule should look inside folders.

- [ ] **Add a rule that domain packages do not import vendor or platform adapters.** rat-stack has `no-core-adapters` for this. Add a `layout()` option (for example `adapterImports`, a list such as `@effect/platform-node`, `@effect/sql-pg`, `effect/unstable/http`) and a Dependency Cruiser rule that only the packages named as plumbing or adapters may import them. This makes `CONTEXT.md:39` (port, layer adapter) checkable. Trippy needs a decision first: `@trippy/db` is plumbing and would be allowed, but `@trippy/trips` imports `Db` and SQL directly, so it stays welded until `trippy/TODO.md:15` is decided. Start with a warn-level rule, or an allow-list that lists today's exceptions.

- [ ] **Write down the shape of a service file.** Add two lines to the add-an-effect-module skill (`SKILL.md:28`) and `AGENTS.md`: one service per file, with its Layer beside it, named after the job. Decide the spelling of the Layer, `Layer.effect(Svc, Effect.gen(...))` in a static member (today's practice) or a `make` member and `static layer` (the page's practice), and test which one the pinned `effect` supports. `packages/trips/src/plans.ts` holds two services and would be the one change to make in Trippy.

- [ ] **Check the manual-runtime ban in tests.** `AGENTS.md:67` bans `Effect.run*` and hand-built runtimes in tests, but `README.md:72` lists it as a prose rule, and `runEffectInsideEffect` only looks inside Effect code. Add an ESLint rule to `packages/rules`, enabled on files under `**/tests/**`, that fails `Effect.runPromise`, `Effect.runSync`, `Effect.runFork` and `ManagedRuntime.make`. Move the line out of the prose rules once it ships.

- [ ] **Bring Trippy's test layout in line with house-rules.** `trippy/AGENTS.md:35` still says tests live in a flat `src/tests/`, while `AGENTS.md:49` here says a `tests/` folder inside the folder it tests. The app's 40 tests in `apps/web/src/tests/` mix MCP, flights, auth and use-cases. Either copy the newer text into Trippy and move the use-case and MCP tests next to their code, or write down why a flat folder stays for Next.js apps. This is a Trippy change, so it belongs in `trippy/TODO.md`, not here.

## 5. Open questions for the owner

1. Is "layers first inside an app" a deliberate choice against the page's "domain, not mechanism"? I read it as yes. The delivery, server and use-cases split is what the fence rests on. If yes, I would add one sentence to `AGENTS.md` or `VISION.md` saying so, so the next reader of the page does not call it a gap.
2. Should a domain package ever import a vendor or platform adapter? Trippy's `@trippy/trips` writes SQL against `SqlClient`. The page, and rat-stack's `no-core-adapters` rule, say no. Trippy's TODO says "only worth it if a second store, or much faster tests, is a real need". Do you want the stack to enforce the boundary anyway, with an allow-list for today's cases?
3. Is a Next.js app one entrypoint (one root, as `runtime.ts` is now), or are the web and MCP routes two? The MCP server Layer is built in delivery today. Moving it to `server/` would match the page, and would cost a small change to the delivery-server exception in `trippy/.dependency-cruiser.cjs:5,28`.
4. The page and rat-stack's own clone disagree on file layout: the page shows domain folders, the clone shows flat files in a domain package. Do you want us to follow the page's tree, or rat-stack's real practice (package per domain, flat inside)? Our packages already follow the second.
5. Do you want a lifecycle or state-machine rule at all? We have none, and no module needs one yet. Trip "frozen versus active" state (`CONTEXT.md:35`) is the nearest case, and it is a policy state, not a lifecycle. I would skip it until a real case appears.
6. Trippy's `AGENTS.md` is a copy that has drifted (it still says "drunk-cat-stack" at line 3 and keeps the flat test rule at line 35). Should it be brought in line with house-rules `AGENTS.md`, or is it meant to differ?
